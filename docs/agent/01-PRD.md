## 1. Product in one paragraph

RetroAlpha is an AI agent team that surveys real Houston or LA buildings from the sky (Vexcel) and from the inside (Matterport), combines that with CoStar building records, decides which carbon-cutting upgrades each building can physically take, prices them through the quant engine, and composes the owner's workspace on the spot. There is **no chatbot and no voice**. The owner sets a goal and acts on widgets; the agents re-plan and rebuild the view.

**Pitch line:** "The cheapest path to your carbon target, found by an agent that looks at the building."

## 2. Problem this role solves

Building owners don't decarbonize because they can't see which upgrades their buildings can take. This role produces the **evidence**: for each building, a verified list of feasible upgrades with sizes, reasons, confidence, and the exact images that support each claim. Without it, the quant engine has nothing real to price.

## 3. Users

| User | What they need from the agent |
|---|---|
| Building owner / asset manager (primary) | Set a CO₂ target, budget, risk appetite; see what each building can take and why; approve a plan |
| CoStar judges | AI at the center pulling from 2–3 data layers, deciding and acting, composing UI; spatial + visual understanding |
| Amazon judges | Multi-step agents that reason, plan, act, adapt; simple UX |
| Track judges (Sustainability) | Real emissions cut, real buildings, works end to end |

## 4. Goals

1. Survey 6–10 real buildings in one city, with at least one "hero" building that has all three data layers.
2. For each building, output a **feasible upgrade list** with size, reason, confidence, and evidence image IDs.
3. Every claim is checked by a **verifier** against its image and CoStar fields.
4. Drive the quant engine (pricing agent) and Nessie (finance agent) through tools; never invent numbers.
5. **Compose the UI**: return a layout JSON choosing widgets from a fixed registry, filled with tool outputs, with one line on why each is shown.
6. Stream a live **activity feed** that makes the agentic depth visible.
7. Run fully offline from cache during judging.

## 5. Non-goals

- No chatbot, no free-text conversation, no voice.
- No separate database for CoStar data (JSON files on the server only).
- No numbers generated by an LLM. LLMs extract observations and write words; code and the engine produce numbers.
- Not building the quant engine math, frontend rendering, or Nessie seeding (other owners).
- Not covering cities other than Houston or LA.

## 6. Functional requirements

### 6.1 Data access (CoStar toolkit)
- **FR-1** Pull building profiles from the CoStar Data Platform: size, year built, type, class, stories, occupancy, location, footprint if available.
- **FR-2** Pull Vexcel overhead imagery around a building (WKT point + buffer) and oblique imagery per facade (footprint polygon + N/E/S/W).
- **FR-3** Find Matterport models for the hero building; pull panoramas, room boundaries, room types, wall graph, and the MatterPak (OBJ mesh + floor plan).
- **FR-4** Cache every toolkit response to disk; support a read-only cache mode for the demo.
- **FR-5** Pick the demo portfolio: 6–10 buildings, one city, all with Vexcel coverage, ≥1 with Matterport.

### 6.2 Agents
- **FR-6 Orchestrator:** turns the owner's goal into plan steps, fans out surveys in parallel, collects results, re-plans on every owner action, triggers memo writing.
- **FR-7 Records analyst:** builds `profile.json` from CoStar fields.
- **FR-8 Aerial inspector:** from overhead + oblique images, reports usable roof fraction, shading, existing solar, roof color, roof type, and windows/glazing per facade orientation.
- **FR-9 Interior inspector (hero building, MVP):** from panoramas + room data, reports lighting type, visible HVAC, window type, floor area, envelope area.
- **FR-10 Site engineer:** applies feasibility rules to inspector findings → feasible upgrades with sizes (kW solar, sq ft insulation, etc.).
- **FR-11 Verifier:** scores each claim 0–1 against its image and CoStar fields; < 0.7 sends a specific question back to the inspector; after 2 loops the claim is `unverified` and excluded from optimization unless the owner includes it.
- **FR-12 Pricing agent:** calls engine tools `simulate`, `get_macc`, `optimize`, `set_assumption`; returns JSON only.
- **FR-13 UI composer:** picks and orders widgets from the registry for the current situation; output validated against schemas.
- **FR-14 Finance agent:** after explicit owner approval only, calls Nessie functions (bills, create account, transfer, pay bill).
- **FR-15 Memo writer:** investment memo whose every number comes from engine output.

### 6.3 Owner interaction (no chatbot)
- **FR-16** Goal form input: city/portfolio, CO₂ target %, budget, risk appetite (λ).
- **FR-17** Widget actions: exclude building, toggle upgrade, click a curve bar, move target slider, approve. Each triggers re-plan + re-compose.
- **FR-18** Approval gate: no Nessie write before an `approve` action carrying a `plan_id`.

### 6.4 Observability
- **FR-19** Activity feed: structured events streamed to the frontend (e.g. "Aerial inspector · Harbor Lofts · south facade · 42 windows").
- **FR-20** Replay mode: stream cached events with realistic delays so the demo looks live offline.

## 10. Constraints

- Python only on the backend. FastAPI.
- Houston and LA data only. Pick one city for the demo.
- Gemini API and Vultr hosting confirmed allowed by CoStar.
- Rate limits: survey at most 3–4 buildings at once; cap loops and steps per agent.
- API keys never reach the browser.
